## BLOCKER — D97 `LATEST_PT_SELECTION_METADATA_LAGS_ONE_EPOCH`
`run_one()` saves `latest.pt` **before** updating `best/best_epoch/bad` (runner lines 180-195), so the
resume checkpoint's selection metadata always describes the **previous** epoch.

Observed right now:
```
best.pt    : epoch=29  macro=0.581710      <- true best model, on disk
latest.pt  : epoch=29  best=0.575372 best_epoch=25 bad=3
registry   : current_epoch=29 best_epoch=29 best_metric=0.581710
```
Epoch 29 **was** an improving epoch, so resuming as-is would:
1. restore `best` 0.581710 → **0.575372** (understated by 0.006338);
2. make any future epoch with macro in (0.575372, 0.581710) satisfy `macro > best` and **overwrite
   `best.pt` with a worse model** — destroying the genuine epoch-29 checkpoint, irreversibly;
3. restore `bad` 0 → **3**, firing patience-15 early stopping 3 epochs early.

Both are silent scientific errors in a headline baseline → **protocol-invalidating**. Per WO §3 the
correct action is STOP, not resume. Nothing was modified; no approval-free fix exists (a fix touches the
frozen runner, and reconciling `latest.pt` is a checkpoint write).

Prior resumes were lucky: at 16:47 the last completed epoch (21) was **not** improving, so `best` was
already current and rc=1/2/3 caused no regression.
